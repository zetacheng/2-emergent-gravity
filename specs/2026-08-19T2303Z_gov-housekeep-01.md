## 6. NEW MECHANISM — disposition of `INCONCLUSIVE` results

### 6.1 The problem this addresses

`PASS` and `FAIL` are self-closing: each yields a conclusion and the work
proceeds. **`INCONCLUSIVE` creates an obligation with no owner and no
closing condition**, and is discharged only by someone remembering it.

This is not hypothetical in this repository. `P2-RECON-01B-B0`'s
re-measurement was executed, verified, and never integrated; the landed
baseline is still the earlier assessment. No one objected — no one carried it.

**The deeper problem, and the one this mechanism is for.** "Present evidence
is insufficient to complete the proof" is being treated as a terminus, when
in research it is often the starting point for "what exactly is still
missing?" Those are different epistemic states, and the programme has not
distinguished them.

`P2-RECON-PROJ-01`'s `Q1` is the case that surfaced it. A Ward identity and a
trace identity are already in the manuscript, and they already yield a
conclusion of the shape the test asks for. What is missing is a
correspondence between two bases, and possibly a relation between two
regimes — finite, explicit, and separately investigable. **That is not the
same state as not knowing the answer**, and recording both as bare
`INCONCLUSIVE` loses the difference.

**The governance so far has been good at preventing false positives.** This
adds the other half: not letting a line stop permanently at `INCONCLUSIVE`
because the executor correctly declined to take the last step.

### 6.2 What is NOT changed

**The prohibition on promoting a result that fails a pre-registered test
stands unchanged.** A test that returns `INCONCLUSIVE` because a required
part was not satisfied must continue to return `INCONCLUSIVE`. Nothing here
licenses relaxing a criterion after seeing the evidence.

**The gap being closed is on the disposition side, not the verdict side.**
The Researcher wrote the prohibition without the matching closure
requirement; this is the missing half.

### 6.3 The mechanism, as ruled

The governing rule, landed verbatim:

> An `INCONCLUSIVE` finding is not terminal when the assessment identifies a
> finite, explicit set of missing bridges whose establishment could change
> the result to a positive finding.

Every `INCONCLUSIVE` result carries one of two subclasses, assigned when the
result is recorded:

    INCONCLUSIVE — CONSTRUCTIVE GAP IDENTIFIED
        A candidate positive argument already exists, and what is missing is
        a finite, explicit, separately investigable set of bridges.

    INCONCLUSIVE — EVIDENCE INSUFFICIENT
        No clear next step is identified. This is the genuine "set aside"
        case.

**Assigning a subclass is required, not optional.** A result recorded as
`INCONCLUSIVE` without a subclass is incomplete.

### 6.3a The required field

Every `INCONCLUSIVE` assessment answers, as a named field:

    Resolution path
        What is the minimum additional derivation, measurement,
        construction, or evidence that would be sufficient to RESOLVE this
        finding?

**The executor defines the path. The executor does not walk it.** Supplying
the missing bridge is theory construction and remains prohibited within a
verification task; §6.2's prohibition is unchanged and this field does not
soften it.

**The path is symmetric, and this is deliberate.** Resolving a finding may
upgrade it, and may equally refute it — establishing that the missing bridge
does *not* hold is a resolution. A field that asked only what would make a
finding positive would bias the definition of the gap toward the answer
wanted, which is the failure mode this programme's governance exists to
prevent, arriving from the other side. **A `Resolution path` that names only
the confirming outcome is incomplete.**

### 6.3b The workflow this enables

    verification
      -> INCONCLUSIVE with subclass and Resolution path
      -> constructive-gap extraction
      -> bounded derivation or measurement task
      -> re-verification

The bounded task is separate from the verification that identified the gap,
and is not performed by it. **Its outcome is not predetermined**: a bounded
task opened on a constructive gap may return a negative result, and that is a
completed task, not a failure of the mechanism.

### 6.4 The PI decision file

A decision file is created in `decisions/`, Part 1 recording:

- what was decided: that `INCONCLUSIVE` results carry a subclass per §6.3
  and a `Resolution path` per §6.3a, and that such a finding is not terminal
  when a finite explicit set of missing bridges is identified;
- who: the PI, this session;
- effect and scope: applies to results recorded from this landing forward;
- that the mechanism was proposed by the Researcher and approved by the PI,
  and that §6.2's prohibition is unchanged;
- the evidence that motivated it, naming the unintegrated re-measurement.

Part 2 carries the review if supplied, and `REVIEW PENDING` if not — which
under §5.1 does not delay effect.

### 6.5 Retrospective application

**The mechanism is prospective.** Existing `INCONCLUSIVE` records are not
retroactively subclassified by this task. The backsweep that classifies them
is a separate measurement task, and **its result is not assumed here**: how
many existing records are scoped is unmeasured, and this specification does
not estimate it.
